# 决策日志 — REQ-7080 Director 子系统模块化拆分

## D-01：三阶段拆分策略

- **决策点**：Director 子系统拆分采用几阶段策略
- **选项**：
  - A: 一次性全量重构（风险高，回滚难）
  - B: 两阶段（先内后外，缺少外部解耦阶段）
  - C: 三阶段（runtime 内部分目录 → 抽取独立子模块 → 解耦外部依赖）
- **选择**：方案 C（三阶段）
- **理由**：
  1. 渐进式拆分，每阶段可独立验证和提交
  2. 阶段1 先解决最大痛点（runtime/ 46 文件），单独交付价值
  3. 阶段2 建立 facade 体系后才进入阶段3 接口化，顺序合理
  4. 每阶段失败可独立回滚，不影响其他阶段
- **日期**：2026-07-17
- **决策者**：用户

## D-02：runtime/ 内部分目录策略

- **决策点**：runtime/ 46 个文件的子目录划分方案
- **选项**：
  - A: 按文件大小分组（大文件一组，小文件一组）
  - B: 按字母顺序分组
  - C: 按逻辑职责分组（core/takeover/workspace/projection/persistence/utils）
- **选择**：方案 C（按逻辑职责分组）
- **理由**：
  1. 按职责分组后每个子目录内聚性高，易于理解和导航
  2. takeover（11文件）和 workspace（6文件）已经是自然的概念边界
  3. 与已有子目录（phases/、recovery/、commands/）的命名风格一致
  4. 缩小了每个目录的文件数到 ≤13，满足项目约束
- **日期**：2026-07-17
- **决策者**：用户

## D-03：超大文件拆分粒度

- **决策点**：5 个超大文件（>650 行）的拆分目标粒度
- **选项**：
  - A: 拆为 ≤200 行（激进，可能过度碎片化）
  - B: 拆为 ≤400 行（平衡，接近项目 ~600 行目标的缓冲）
  - C: 拆为 ≤600 行（保守，仅做微量拆分）
- **选择**：方案 B（≤400 行）
- **理由**：
  1. 400 行是合理缓冲区，低于项目 ~600 行目标
  2. 不追求过度碎片化（如 200 行上限），避免函数调用链过长
  3. 每个拆分模块聚焦单一职责
- **日期**：2026-07-17
- **决策者**：用户

## D-04：外部引用路径策略

- **决策点**：外部文件引用 director 内部文件使用什么路径
- **选项**：
  - A: 允许深路径导入（如 `director/runtime/core/DirectorRuntimeService.ts`）
  - B: 强制通过 facade 导入（如 `director` 或 `director/runtime`）
- **选择**：方案 B（强制 facade 导入）
- **理由**：
  1. 符合项目"通过 facade/index.ts 消费，不深导入内部文件"的架构约束
  2. 未来内部重组时仅需更新 facade，外部不受影响
  3. 降低外部对内部实现的认知负担
- **日期**：2026-07-17
- **决策者**：用户

## D-05：接口抽象范围

- **决策点**：阶段3 接口解耦的抽象程度
- **选项**：
  - A: 为所有外部依赖创建完整接口（过度工程化）
  - B: 只为 directorRuntimeTools 和 directorWorker 创建最小接口
  - C: 不做接口抽象，仅减少 import
- **选择**：方案 B（最小接口）
- **理由**：
  1. YAGNI — 当前仅两个外部耦合点需要接口化
  2. directorRuntimeTools（536 行）是最重的耦合点，收益最高
  3. directorWorker 可以通过事件驱动解耦，不需要新接口
  4. 避免创建"万能接口"导致接口脆弱
- **日期**：2026-07-17
- **决策者**：用户
