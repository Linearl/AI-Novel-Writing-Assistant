# 决策日志

## D1: 选择 MachineGuid 替代 MAC 地址

- **日期**：2026-07-18
- **决策点**：加密密钥源选型
- **选项**：
  - A: Windows MachineGuid + /etc/machine-id
  - B: 去掉加密，对齐上游明文存储
  - C: 使用 CPU ID / 磁盘 UUID
- **选择**：A
- **理由**：
  - MachineGuid 在系统安装时生成，终身不变（除非重装系统）
  - /etc/machine-id 是 Linux 标准的机器标识方案
  - 保留加密安全性（方案 B 降低安全性）
  - CPU ID / 磁盘 UUID 在容器/虚拟化环境中不稳定
- **风险**：Windows 重装系统后 MachineGuid 变化（与 MAC 方案同等风险，可接受）

## D2: 解密失败返回 null 而非密文

- **日期**：2026-07-18
- **决策点**：解密失败的降级策略
- **选项**：
  - A: 返回密文原文（当前实现）→ LLM 报 "Invalid API Key"
  - B: 返回 null → 上层报 "未配置 API Key" → 用户重新输入
  - C: 抛异常 → 阻断启动
- **选择**：B
- **理由**：
  - 方案 A 导致用户看到"key 失效"但不理解原因（当前 bug）
  - 方案 C 过于激进，一个 provider key 问题不应阻断整个服务
  - 方案 B 给出清晰的"未配置"提示，引导用户重新输入
- **风险**：用户需手动重新输入 API Key（一次性操作，可接受）

## D3: 保留旧密钥兼容迁移

- **日期**：2026-07-18
- **决策点**：是否自动迁移旧密文
- **选项**：
  - A: 不迁移，强制用户重新输入
  - B: 自动用旧密钥解密后用新密钥重新加密
  - C: 提供 CLI 迁移工具
- **选择**：B
- **理由**：
  - 用户体验最佳，无需手动操作
  - 实现简单：`migrateExistingKeys()` 已有扫描逻辑，扩展即可
  - 旧密钥派生函数保留为 `legacyDeriveMachineKey()`，仅迁移期使用
- **风险**：如果旧密钥也不可用（如 MAC 地址已变化），降级为方案 A（删除密文）
