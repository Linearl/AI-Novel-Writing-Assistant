# REQ-7069: Auto-Director 增强 — 决策日志

## 决策1: 创建向导实现方式

**决策日期**：2026-07-14

**背景**：5 步创建向导应直接移植上游实现还是重新设计？

**选项**：
- **方案A**: 直接移植上游 `autoDirector/` 目录下 9 个文件，适配接口差异
- **方案B**: 参考上游思路但重新设计 UI 和状态管理
- **方案C**: 使用现成的多步表单库（如 react-step-wizard）

**决策**：✅ ~~方案A~~ → **已更新为 D6~D10 的方案 C 变体**（见决策 6）

**理由（原）**：
1. 上游实现完整（9 个文件、约 2000 行），经验证可用
2. 本项目与上游使用相同技术栈（React + TypeScript）
3. 直接移植成本最低，只需适配 API 调用和路由差异
4. 避免引入新依赖

**更新说明（2026-07-16）**：经对比分析，发现现有 `NovelAutoDirectorDialog` 已实现与上游相同的核心逻辑（3 个 hook，885 行），但 UI 组织为紧凑面板模式。上游 Wizard 是独立全页面（多路由入口），与现有单路由 Modal 入口冲突。方案调整为"提取共享 controller + 步骤 UI 作为 Modal 展开形态"。

## 决策2: 通知轮询策略

**决策日期**：2026-07-14

**背景**：桌面通知的轮询频率和策略如何选择？

**选项**：
- **方案A**: 固定 15 秒轮询（简单）
- **方案B**: 基于 SSE/WebSocket 实时推送（复杂但精确）
- **方案C**: 15 秒轮询 + 页面不可见时降频（平衡）

**决策**：✅ 方案C（后续实现）

**理由**：
1. SSE/WebSocket 需要服务端改造，成本过高
2. 固定轮询在页面不可见时浪费资源
3. 页面不可见时增加通知频率确保用户回来时能收到最新状态
4. 与上游实现一致

## 决策6: 与现有 NovelCreate 流程的整合方式（新增）

**决策日期**：2026-07-16

**背景**：现有 `NovelCreate.tsx` 已实现三路径创建，路径 A "我有初步想法" 通过 `NovelAutoDirectorDialog`（模态对话框）完成所有设置。上游 `AutoDirectorCreatePage` 是独立全页面（独立路由 `/novels/auto-director`），5 步顺序展开。两者核心控制器逻辑 90% 相同，差异仅在 UI 组织方式和路由结构。

**选项**：
- **方案A**: 废弃现有 Modal，全量替换为上游 Wizard 独立页面
- **方案B**: 保留 Modal，新增 Wizard 页面作为补充入口，两者共存
- **方案C**: 提取共享 controller，Wizard 步骤栏作为 Modal 的展开引导形态

**决策**：✅ 方案C

**理由**：
1. 方案A 会破坏现有"QuickPreview → 回填 idea → 直接生成候选"的快捷路径
2. 方案B 引入两份 UI 代码和维护成本，且需要管理两个路由入口的 workflowTask 同步
3. 方案C 保留现有所有交互路径，只改变 Modal 内部的 UI 组织方式

**影响**：
- 重构现有 3 个 hook 为统一 `useAutoDirectorCreateController`
- 新增 5 个 Stage 组件 + 1 个步骤摘要栏
- 不引入新路由、不改变外部调用方式
- 预计 3.5 天（对比原方案的 5-6 天，减少约 40%，因为移除了 FR-2~FR-7）

## 决策7: Controller 策略（新增）

**决策日期**：2026-07-16

**背景**：现有 3 个独立 hook（useDirectorTaskQuery / useDirectorWorkflowMutations / useNovelAutoDirectorCandidateMutations）合计 885 行，逻辑与上游 `useAutoDirectorCreateController`（612 行）90% 相同。应直接复用还是重构？

**选项**：
- **方案A**: 直接复用上游 controller 代码，适配接口差异
- **方案B**: 重构现有 3 个 hook 为统一 controller，参考上游但不复制

**决策**：✅ 方案B

**理由**：
1. 现有代码已跑通验证，重构风险可控
2. 上游 controller 与现有 API 调用方式有细微差异（如 bootstrap/confirm 参数结构），适配成本接近重写
3. 重构过程中可以清理 3 个 hook 之间的状态同步冗余

**影响**：
- 新建 1 个 controller 文件替代 3 个 hook 文件
- 如 controller 文件超过 600 行，按职责拆分子模块（core / mutations / candidates）

## 决策9: 步骤状态持久化（新增）

**决策日期**：2026-07-16

**背景**：步骤进度是否需要在 Modal 关闭后保持？

**选项**：
- **方案A**: localStorage 持久化（跨会话恢复）
- **方案B**: 仅 React state（Modal 关闭即丢失）

**决策**：✅ 方案B

**理由**：
1. 步骤 1-4 是纯前端配置，不涉及服务端持久化
2. 用户确认候选后，全部状态由 workflowTask 承载
3. localStorage 持久化需要处理多任务去重、过期清理等额外复杂度

## 决策10: FR-2~FR-7 范围拆分（新增）

**决策日期**：2026-07-16

**背景**：原任务包包含 7 个子功能（FR-1 创建向导 / FR-2 桌面通知 / FR-3 待审自动提升 / FR-4 散文质量检测 / FR-5 冲突曲线 / FR-6 待审上下文 / FR-7 资源上下文重构），预估 5-6 天。FR-1 的整合方案分析后，其余子功能如何处理？

- **方案B**: 本任务包只做 FR-1，FR-2~FR-7 拆到独立任务包

**决策**：✅ 方案B

3. 独立任务包便于 review、测试和回滚
4. FR-5 与 REQ-7063 存在依赖关系（决策5），需要等 7063 先行
