# 决策日志 — REQ-7081 统一编排层

## 决策 1：统一编排方案选择

- **决策点**：四套编排系统的收敛方案
- **选项A**：建立 `orchestration/` 顶层统一入口，router 分发 + 共享 ExecutionContext
- **选项B**：编写 Architecture Decision Record (ADR)，逐步在现有结构中建立调用规范
- **选择**：方案A
- **理由**：
  - 方案A 从根本上解决"四轨并行"问题，统一入口避免了选择逻辑散落
  - 方案B 仅靠文档规范约束，不解决路径分散和状态隔离问题
  - 方案A 的 facade 兼容层保证平滑迁移，不立即破坏现有行为
  - 方案A 的 ExecutionContext 设计为后续跨系统协调提供了基础设施
- **日期**：2026-07-17
- **决策者**：用户（已确认）

## 决策 2：迁移顺序

- **决策点**：四套子系统的迁移顺序
- **选项A**：pipeline 先迁移（最大子系统，先啃硬骨头）
- **选项B**：graph → runtime → agent → pipeline（从小到大的渐进式）
- **选择**：方案B
- **理由**：
  - graph 子系统文件最少（~13），依赖最少，迁移风险最低
  - 从小到大的顺序允许每步验证，问题定位更精确
  - pipeline 放在最后是因为：1) 依赖 R7080 拆分完成；2) 文件最多（~101），导入路径影响面最大
  - 先完成前三个子系统可以为 pipeline 迁移积累经验
- **日期**：2026-07-17
- **决策者**：AI 分析 + 任务设计

## 决策 3：Facade 兼容策略

- **决策点**：迁移后旧路径如何处理
- **选项A**：立即删除旧目录，强制一次性更新所有导入路径
- **选项B**：保留 facade 兼容层至少一个版本，后续逐步清理
- **选择**：方案B
- **理由**：
  - 方案A 风险高，任何一处导入遗漏都会导致编译/运行时错误
  - 方案B 通过 facade 重新导出保证平滑过渡
  - facade 添加 `@deprecated` 注释可选启发后续清理
  - 实际经验表明一次性 clean cut 在 ~200 文件的迁移中几乎必然遗漏
- **日期**：2026-07-17
- **决策者**：AI 分析

## 决策 4：pipeline 迁移前置依赖

- **决策点**：pipeline 迁移是否必须等 R7080 完成
- **选项A**：不等，直接在原始 director/ 结构上迁移
- **选项B**：等待 R7080 Director 拆分至少阶段1完成后再迁移
- **选择**：方案B
- **理由**：
  - director/ 是最大的子系统（~101 文件），直接迁移风险过高
  - R7080 拆分后模块结构更清晰，迁移时可保持此结构
  - 如果不等 R7080，迁移后可能还需再次调整目录结构（二次迁移）
  - 其他三个子系统的迁移可先行推进，不阻塞整体进度
- **日期**：2026-07-17
- **决策者**：用户 + AI 分析
