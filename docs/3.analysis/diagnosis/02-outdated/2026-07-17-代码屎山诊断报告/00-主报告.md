## 二、平行系统（Parallel Systems）— 最严重的屎山模式

### 2.1 Director 系统膨胀 [P0-架构阻塞]

`services/novel/director/` 是整个项目的最大痛点：**101 个文件，13 个子目录**。

| 子目录 | 文件数 | 职责 |
|--------|--------|------|
| `runtime/` | 46 | 运行时状态、持久化、工作台分析、接管 |
| `workflowStepRuntime/` | 16 | 工作步骤模块、注册表 |
| `phases/` | 12 | 候选、执行、修复、质量循环 |
| `projections/` | 10 | 投影、仪表盘、进度追踪 |
| `automation/` | 9 | 自动执行、检查点、断路器 |
| `recovery/` | 5 | 恢复、回填 |
| `commands/` | 5 | 命令解释器、租约管理 |
| `state/` | 4 | 状态提交、读取 |
| 其他 | 4 | debug、http、langgraphPilot、operations |

**问题**：单个子目录（`runtime/`）就有 46 个文件，已经超出 CLAUDE.md 的 ">12 个文件必须建下级目录" 约束 4 倍。Director 已成为一个"项目中的项目"，难以理解和维护。

**根因**：auto-director 功能在多个版本中不断叠加（自动化、接管、质量循环、恢复、投影），但从未做系统性拆分。

### 2.2 四套编排系统并行 [P0-架构阻塞]

项目同时存在四套不同的编排机制：

| 系统 | 位置 | 职责 | 状态 |
|------|------|------|------|
| Agent Orchestrator | `agents/orchestrator.ts` | Agent-based 编排、工具调用 | 活跃 |
| Runtime Layer | `runtime/` + `services/novel/runtime/` | DI、任务分发、运行时上下文 | 活跃 |
| LangGraph Graphs | `graphs/` + `creativeHub/` | 图编排（角色设计、大纲、写作公式） | 活跃 |
| Director Pipeline | `services/novel/director/` | 章节生成流水线 | 活跃 |

**问题**：同一类"执行一个 AI 流程"的操作，可能走 Agent → Director Pipeline → LangGraph 三条不同路径。新人（包括 AI）无法从代码结构推断应该用哪套。

**根因**：LangGraph 是后引入的，未替代原有编排；Agent 层是 creative hub 专用的，与 director 各自演进。

### 2.3 Pipeline 服务四件套 [P1-功能重叠]

`services/novel/` 下存在四个 pipeline 相关服务：

| 文件 | 行数 | 状态 |
|------|------|------|
| `NovelPipelineService.ts` | 65 | **@deprecated**，facade 封装 |
| `novelCorePipelineService.ts` | 568 | 核心 pipeline 逻辑 |
| `novelCorePipelineExecutor.ts` | 610 | pipeline 执行器 |
| `NovelPipelineRuntimeService.ts` | 108 | pipeline 运行时 |

其中 `NovelPipelineService` 已标记 `@deprecated`，但仍在被引用（约 65 行的纯 facade）。`novelCorePipelineService` 和 `novelCorePipelineExecutor` 职责边界不清——两者都超过 500 行，都在处理 pipeline 执行逻辑。

### 2.4 NovelService + NovelCoreService 双层 [P1-facade 遗留]

- `NovelCoreService.ts`：实际业务逻辑入口，组合 7 个子服务
