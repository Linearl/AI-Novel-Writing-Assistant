# 子报告2：四套编排系统并行

> 严重度：P0（架构阻塞）
> 范围：server/src 全局编排机制

---

## 一、四套系统概览

### 1.1 系统清单

| # | 系统 | 入口位置 | 文件数 | 核心能力 |
|---|------|----------|--------|----------|
| 1 | Agent Orchestrator | `agents/orchestrator.ts` | ~50 | Agent-based 对话编排、工具调用、意图解析 |
| 2 | Runtime Layer | `runtime/` + `services/novel/runtime/` | ~35 | DI 注入、任务分发、运行时上下文 |
| 3 | LangGraph Graphs | `graphs/` + `creativeHub/` | ~13 | 声明式图定义、状态机、节点执行 |
| 4 | Director Pipeline | `services/novel/director/` | ~101 | 章节生成流水线、质量循环、自动执行 |

### 1.2 各系统的触发场景

```
用户请求 → API Route → ???
                          ├── Agent 系统处理？（creativeHub chat）
                          ├── Director Pipeline 处理？（章节生成）
                          ├── LangGraph 处理？（角色设计/大纲/世界观）
                          └── Runtime Layer 分发？（通用任务）
```

**问题**：同一个"执行 AI 任务"的请求，可能走四条不同的路径，且选择逻辑散落在各处。

## 二、各系统详细分析

### 2.1 Agent Orchestrator

**位置**：`server/src/agents/`

**架构**：
```
agents/
├── orchestrator.ts          (入口)
├── planner/                 (意图解析)
│   ├── intentSchema.ts
│   └── parser.ts
├── tools/                   (26个工具文件)
│   ├── directorRuntimeTools.ts   ← 桥接到Director
│   ├── novelProductionTools.ts
│   ├── characterTools.ts
│   └── ...
├── runtime/                 (Agent运行时)
└── catalog.ts               (Agent目录)
```

**核心职责**：
- 接收用户对话消息
- 解析意图（planner）
- 选择并调用工具（tools）
- 管理对话上下文

**与其他系统的耦合**：
- `tools/directorRuntimeTools.ts`（536行）直接调用 Director Runtime 的 API
- `tools/novelProductionTools.ts`（245行）调用 Novel Production 服务
- Agent 系统本质上是 Director 和其他服务的"门面"

### 2.2 Runtime Layer

**位置**：`server/src/runtime/`（2文件）+ `server/src/services/novel/runtime/`（29文件）

**`runtime/`（2文件）**：
- `appPaths.ts` — 应用路径常量
- `memoryTelemetry.ts` — 内存遥测

**`services/novel/runtime/`（29文件）**：
```
runtime/
├── BatchContextCache.ts
├── ChapterRuntimeCoordinator.ts    ← 章节运行时协调
├── ChapterPipelineRuntimeAdapter.ts ← Pipeline适配器
├── ChapterArtifactDeltaService.ts   ← 章节产物增量
├── ChapterContentFinalizationService.ts ← 章节内容定稿
└── ... (24 more)
```

**核心职责**：
- 章节生成的运行时协调
- 批量上下文缓存
- 章节产物的增量同步
- Pipeline 适配层

**问题**：`services/novel/runtime/` 29 个文件本身已超出 CLAUDE.md 的 12 文件阈值 2 倍，且与 `director/runtime/`（46文件）职责高度重叠——两者都在处理"章节生成的运行时"。

### 2.3 LangGraph Graphs

**位置**：`server/src/graphs/`（4文件）+ `server/src/creativeHub/`（9文件）

**graphs/**：
```
graphs/
├── characterDesignGraph.ts    角色设计图
├── novelOutlineGraph.ts       大纲生成图
├── worldBuildingGraph.ts      世界观构建图
└── writingFormulaGraph.ts     写作公式图

**creativeHub/**：
```
creativeHub/
├── CreativeHubLangGraph.ts       ← 主入口
├── CreativeHubInterruptLangGraph.ts

├── CreativeHubService.ts

**核心职责**：

**与其他系统的关系**：

- CreativeHub 是这些图的统一入口
- 与 Director Pipeline 是**平行**关系：Director 处理章节生成，LangGraph 处理前置准备

## 三、职责边界问题

### 3.1 重叠区域

| 功能 | Agent系统 | Runtime层 | LangGraph | Director |
|------|-----------|-----------|-----------|----------|
| 意图解析 | planner | - | - | - |
| 工具调用 | tools/* | - | - | - |
| 任务分发 | - | ChapterRuntimeCoordinator | - | Orchestrator |
| 状态管理 | - | BatchContextCache | langgraphState | DirectorRuntimeStore |
| 执行引擎 | - | ChapterPipelineRuntimeAdapter | Graph nodes | DirectorNodeRunner |
| 质量检查 | - | - | - | QualityLoop |

"执行引擎"一栏有 3 个平行实现（Runtime Adapter / Graph Nodes / Director NodeRunner）。

### 3.2 选择逻辑散落

确定一个请求走哪条路径的逻辑分布在：
- `app.ts`（路由注册）
- `modules/*/http/`（模块入口）
- `agents/orchestrator.ts`（意图路由）
- `services/novel/director/commands/DirectorCommandInterpreter.ts`（命令解释）

没有统一的"编排路由表"。

### 3.3 状态不互通

- Agent 系统有独立的对话状态
- Director 有 `DirectorRuntimeStore`（727行）
- LangGraph 有 `langgraphState.ts`
- Runtime 有 `BatchContextCache`

四套状态系统各自管理，同一任务的不同阶段可能读写不同状态存储。

## 四、根因分析

| 根因 | 证据 |
|------|------|
| LangGraph 后引入未替代旧系统 | `graphs/` 仅 4 文件，Director 有 101 文件；LangGraph 偏声明式，Director 偏过程式 |
| Agent 系统为 CreativeHub 专用 | agents/ 主要被 creativeHub 调用，不服务 Director |
| Director 自成体系 | 101 文件已形成独立生态，有状态管理、命令系统、投影层 |
| Runtime 层是适配器堆叠 | 29 文件多为 adapter/bridge/connector，是粘合代码 |

---

## 五、收敛建议

### 方案A：统一编排层（推荐）

建立 `orchestration/` 顶层目录，作为所有 AI 执行的统一入口：

```
orchestration/
├── router.ts              ← 统一路由：根据任务类型分发
├── agent/                 ← 原 agents/（对话级编排）
├── pipeline/              ← 原 director/（流水线编排）
├── graph/                 ← 原 graphs/ + creativeHub/（图编排）
└── runtime/               ← 原 services/novel/runtime/（运行时协调）
```

工时：20-30h（需要大量导入路径更新）

### 方案B：明确边界不合并

不物理合并，但在架构文档中明确各系统职责边界：

| 系统 | 唯一适用场景 |
|------|-------------|
| Agent | 用户对话交互、意图解析、工具选择 |
| Pipeline (Director) | 章节级批量生成、质量循环 |
| Graph (LangGraph) | 前置准备任务（角色/大纲/世界观/公式） |
| Runtime | 章节运行时协调、缓存、增量同步 |

工时：5-8h（文档 + 代码注释）

**建议先执行方案B（低成本止血），再在后续版本中评估方案A的收益是否值得投入。**
