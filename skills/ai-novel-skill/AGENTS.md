# AI 协作规范

> 本文件定义 AI 的工作方式、协作流程与 Skill 约定。
> Skill 架构、文件结构、命令等事实性信息见根目录 `SKILL.md`。
> 两个文件职责分离：本文件 = **怎么做/什么标准**，`SKILL.md` = **是什么/在哪里**。

---

## 1. AI 工作习惯

### 1.1 交互与沟通

1. 用户提问后先分析并形成简报；不确定项先讨论；使用 `AskUserQuestion` 获取用户意图。
2. 用户提供 URL 时，先读取并提炼关键信息，再执行实现。
3. 用户要求"写文档"时，写入对应文件并在对话中说明文档要点。
4. **思考过程必须使用中文推理**（命令、路径、代码符号、变量名保持原文）。

### 1.2 任务规划与执行

1. 简单、边界清晰的单点任务可直接执行，不强制进入 Plan mode。
2. 规划产物（步骤/决策/待办）必须文档化，并按文档规范落位。
3. 以"问题/异常"发起任务时，默认按 **问题 → 诊断 → 需求 → 任务包 → 开发 → 验证 → 归档** 链路推进。
4. 多条任务按用户指定顺序执行；需调整顺序时先说明理由。
5. 复杂任务优先使用子代理加速并行。

### 1.3 执行策略

1. 过程资产优先落在 `docs/` 工作区。
2. **根因优先**：跨模块、重复出现、涉及正确性/安全/稳定性的问题，先做系统性根因修复。
3. **编码准则**：遵循 Karpathy Guidelines——Think Before Coding、Simplicity First、Surgical Changes、Goal-Driven Execution。
4. 优先复用仓库现有脚本与流程，不引入冲突工作流。
5. 代码审计修复后，**必须**同步更新审计报告、项目 README、`docs/` 相关文档。
6. **写新函数前，必须先 grep 仓库**，已有可复用的优先复用。
7. **证据冲突规则**：grep 与 Read 冲突时，禁止先下结论，必须闭环验证。
8. 发现超过 700 行的非自动生成文件，提醒用户重构（项目约束：单文件目标 ~600 行，>700 必须重构）。

### 1.4 任务收尾

1. 给出完成总结：**已完成内容 + 验证结果 + 后续建议**。
2. 如需继续下一步，给出推荐方案并说明理由。
3. 存在阻塞时，先给默认方案再请求确认。

## 2. 项目约定

### 2.1 文档组织

1. `docs/` 编号分层：`0.version_plan / 1.task / 2.tech / 3.analysis / 4.misc / 5.git-commit / 6.changelog / 7.weekly / 8.test`。
2. 新增/更新文档前，先阅读 `docs/README.md` 与 `docs/INDEX.md`。
3. 分析类文档三层模型：证据（`3.analysis/evidence`）→ 事前分析（`3.analysis/diagnosis`）→ 事后分析（`3.analysis/report`）。
4. 实操顺序：查索引 → 按规范命名落位 → 更新索引入口。

### 2.2 文档可追溯性

1. 功能/脚本/流程变更必须同步文档，结论标注验证依据。
2. 任务流转保留双副本（工作副本 + `-original` 冻结副本）。
3. 任务包必须包含完整六件套（README / REQ-original / REQ / tasks / design / decision_log）。

### 2.3 文档编码

1. 所有 Markdown 统一 UTF-8。

### 2.4 AI 文档落位规则

1. 事前分析 → `3.analysis/diagnosis/`；操作指南 → `2.tech/guide/`；版本更新 → `6.changelog/`；接口变更 → `2.tech/api/`；优化过程 → `1.task/`。
2. 文档命名优先 `YYYY-MM-DD-主题.md`，禁用临时命名。

## 3. AI 行为准则

### 六条铁律

1. **修 Bug 主动检查相关代码**：修复 bug 时，必须搜索并检查调用方、同模块、同类逻辑，不得只修眼前一处。
2. **编辑后跑类型检查**：每次编辑 TypeScript 代码后，执行 `pnpm typecheck`，确保无新增类型错误。
3. **回复简洁不废话**：直奔主题，不加无意义开场白和结尾语。
4. **大改动先输出计划**：多文件、架构调整或新功能，先输出实施计划再动手。
5. **不确定主动说**：对需求/边界/方案不确定时，主动声明并提问。
6. **新功能必须有测试**：新功能或关键 bug 修复，必须同步编写测试。

### 编码最佳实践

- **先读后改**：修改前必须阅读完整上下文，理解现有模式再动手。
- **错误处理显式化**：禁止空 `catch` 或静默吞错。
- **函数短小聚焦**：20-50 行以内，单一职责；超过 4 层嵌套必须拆分。
- **命名即文档**：变量、函数命名自解释意图。
- **安全零容忍**：禁止硬编码密钥/密码；用户输入校验；SQL 参数化。
- **依赖审慎引入**：新增依赖前询问用户。
- **不可变优先**：优先不可变数据和纯函数。
- **禁止过度抽象**：简单直接优于精巧分层。
- **禁止超前设计**：不预想用户用不到的复杂场景。
- **禁止过度防御性编程**：参数校验收敛到外部接口入口。

### Skill 特有约束

- **Claude-Native 原则**：意图识别、任务分类、规划、路由、工具选择等决策路径必须以 Claude 结构化理解为主要实现方式。
- **Prompt Governance**：新增产品级 prompt 只能进入 `references/`，并按契约治理。
- **质量门**：章节审核、验收和质量循环结果不能自动阻断全局执行链。
- **数据保护**：执行任何破坏性数据操作前，必须获取用户明确批准 → 完成备份 → 验证备份可恢复。
- **UI 文案规则**：所有面向用户的 UI 文案必须从用户视角说明功能，禁止使用实现叙述式文案。

## 4. 修改后必做（验证清单）

每次修改代码后，**必须按顺序执行**：

### Python 脚本修改

1. ✅ 语法检查：`python -m py_compile <script>`
2. ✅ 单元测试：`python -m pytest tests/ -v`

### 参考文档修改

1. ✅ 格式检查：Markdown 语法正确
2. ✅ 交叉引用检查：链接有效

### 全量验证

1. ✅ 完整性检查：所有文件存在且非空
2. ✅ 格式一致性：文件命名规范

## 5. 调试标准流程

### 脚本调试

1. 查看脚本输出：控制台日志
2. 检查文件状态：`ls -la <workspace>/`
3. 检查 YAML 有效性：`python -c "import yaml; yaml.safe_load(open('<file>.yaml'))"`
4. 单步调试：`python -m pdb <script>`

### 常见问题排查

| 现象 | 可能原因 | 排查步骤 |
|------|----------|----------|
| Skill 无法激活 | SKILL.md 格式错误 | 检查 YAML front matter |
| 脚本执行失败 | Python 依赖缺失 | `pip install -r requirements.txt` |
| 文件未生成 | 路径错误或权限问题 | 检查目录权限和路径 |
| YAML 解析失败 | 格式错误 | 用 yaml.safe_load 验证 |
| 状态丢失 | checkpoint 损坏 | 从 YAML 恢复 |
